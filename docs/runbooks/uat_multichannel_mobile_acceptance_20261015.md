# DirectPilot — اجرای هم‌زمان DM/Story/Comment و پذیرش ناوبری موبایل UAT

**محیط پذیرش یکتا:** `https://uat.directpilot.ir`؛ کاربر آزمایشی و احراز هویت قانونی Vercel. سناریوهای ارسال واقعی Meta خارج از تست امن فعلی هستند و تا فراهم‌شدن حساب/اجازه واقعی **BLOCKED** محسوب می‌شوند.

## رفتار دقیق فعلی — بدون فرض Rule چندکاناله در Backend

Frontend `components/automation-rules-workspace.tsx` (F#12) چک‌باکس `DM_KEYWORD`, `STORY_REPLY_KEYWORD`, `COMMENT_KEYWORD` دارد؛ کاربر **یک، دو یا سه محل** انتخاب می‌کند. حالت اولیه `DM_KEYWORD` است. `triggerOptions` ترتیب پردازش را **DM سپس Story سپس Comment** مشخص می‌کند. هر انتخاب روی سرور **یک قانون مستقل** است؛ نه یک قانون واحد با چند Trigger.

| منبع | مقدار Backend | عملیات مجاز |
|---|---|---|
| پیام مستقیم | `DM_KEYWORD` | `SEND_MESSAGE` |
| پاسخ استوری | `STORY_REPLY_KEYWORD` | `SEND_MESSAGE` |
| کامنت | `COMMENT_KEYWORD` | `SEND_PRIVATE_MESSAGE` (پیام خصوصی برای کامنت) |

- حداقل یک محل باید انتخاب شود. نام، کلیدواژه، متن پاسخ، اولویت، وضعیت و تطبیق باید معتبر باشند.
- محدودیت پلن: هر محل **یک Rule از ظرفیت** `automation_limit` کم می‌کند؛ انتخاب ۳ محل روی پلن سه‌قانونی، کل ظرفیت را مصرف می‌کند. Frontend با `rules.length + extraCount > limit` کنترل اولیه دارد؛ Backend باید جداگانه Fail-Closed باشد.
- Create با سه محل سه `create()` **ترتیبی** می‌زند (نه Parallel). Edit یک Rule قدیمی فقط اولین منبع انتخابی را **update** می‌کند؛ انتخاب‌های اضافی Ruleهای جدید می‌سازند. تغییر Rule قبلی به سه محل الزاماً Rules هم‌نام موجود دیگر را حذف/گروه‌بندی نمی‌کند.
- Multi-create اتمیک نیست؛ اگر Rule دوم/سوم شکست بخورد Ruleهای قبلی می‌توانند باقی بمانند. UI تعداد موفق‌ها را نشان می‌دهد، فهرست را Refresh می‌کند و Retry کور کل گروه را ممنوع می‌کند. این رفتار باید در UX شفاف باشد؛ یک قابلیت «حذف گروهی» یا «Atomic batch» فعلاً ادعا نشود.
- Meta UAT end-to-end در گذشته برای تک‌کاناله گزارش PASS شده بود؛ **برابر با تأیید سه‌کاناله جدید نیست**. ارسال واقعی DM/Story/Comment نیازمند اتصال، مجوز و تأیید جداست.

## AC-MULTI — تست دستی و ریسک

- [ ] انتخاب DM به‌تنهایی → ۱ Rule با `SEND_MESSAGE`، ویرایش/حذف درست و شمارنده ظرفیت صحیح.
- [ ] Story به‌تنهایی → ۱ Rule با `SEND_MESSAGE`.
- [ ] Comment به‌تنهایی → ۱ Rule با `SEND_PRIVATE_MESSAGE`.
- [ ] انتخاب DM + Story → دقیقاً ۲ Rule مستقل؛ نمایش نام و منبع در فهرست.
- [ ] انتخاب هر سه → دقیقاً ۳ Rule مستقل، هرکدام یک ظرفیت؛ ذخیره ترتیبی و بازخوانی با API.
- [ ] انتخاب صفر → خطای روشن و عدم ارسال درخواست.
- [ ] ظرفیت ناکافی یا غیرفعال بودن ماژول → عدم دورزدن محدودیت از طریق API؛ خطای توضیحی.
- [ ] ویرایش Rule موجود + انتخاب دوم → یک Update و یک Create، نه دو Rule تکراری مبهم.
- [ ] شبیه‌سازی شکست میانی/409 optimistic lock → موارد قبلاً ثبت‌شده حفظ شوند، لیست Sync و درخواست تکراری کور ارسال نشود؛ در صورت نیاز issue طراحی Atomic batch ثبت شود.
- [ ] تأیید Meta webhook/callback/read/send و Dedup برای هر سه منبع، **فقط با مجوز و حساب آزمایشی**؛ تا آن زمان **BLOCKED**.
